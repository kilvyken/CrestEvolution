# 05 高难代码示例

本文件说明最难部分的设计和仓库内示例位置。示例刻意依赖抽象接口，不猜测游戏内部类型。真正接入游戏时，只替换 `GameInterop`。

## 1. 多层强化与计时

文件：`src/SilkCrestOverhaul/Core/State/TimedStackCounter.cs`

解决：猎手 6/12 层、超级亡怒每 6 刀增长、丝母 1–12 阶段等。

关键点：

- 层数变更和计时刷新分开。
- 时间来源可注入，测试不依赖 Unity `Time.time`。
- 到期只触发一次。
- 阈值事件由模块处理，不把猎手规则写进通用计数器。

```csharp
var stacks = new TimedStackCounter(maxStacks: 12, durationSeconds: 10f, clock);
stacks.Changed += (_, e) => ui.SetStacks(e.Current, e.RemainingSeconds);
stacks.ThresholdReached += (_, e) => ApplyHunterThreshold(e.Threshold);
stacks.Add(1, refreshDuration: true);
```

## 2. 统一伤害管线

文件：`Core/Combat/DamagePipeline.cs`

解决：固定加伤、倍率、暴击、火刀/毒刀、燃爆、剑气、多段攻击和“第一刀必暴”的顺序问题。

建议顺序：

1. 原版基础伤害快照。
2. 攻击类型/纹章动作修正。
3. 蓄力与精准时刻。
4. Buff 与护符倍率。
5. 固定加伤。
6. 暴击判定与暴击倍率。
7. 最终钳制。
8. 生成追加伤害命令；追加伤害默认不重新进入全部触发器。

每个修饰器带 `Id`、`Order`、`SourceTag`，日志可重建计算过程。

## 3. 丝线代替生命承伤

文件：`Core/Combat/SilkShieldPolicy.cs`

解决丝母强化状态。必须在“玩家受伤前”计算，并返回明确的生命伤害、丝线消耗和是否退出强化；不要在多个 Postfix 中分别扣资源。

```text
输入：原始面具伤害、每面具所需丝线、当前丝线
输出：吸收面具数、丝线消耗、剩余生命伤害、是否破盾
```

示例策略按文档暂定：每格伤害消耗 3 丝；足额吸收则不退出，不足则消耗可用丝线、承受剩余伤害并退出。若用户确认不同规则，只改策略类。

## 4. 红/绿/紫/蓝血与碎面甲转换

文件：`Core/Health/MarkedHealthPool.cs`、`HealthConversionService.cs`

所有治疗先形成 `HealTransaction`：

- 原始治疗量；
- 实际白血恢复；
- 溢出量；
- 转入红/绿/紫/蓝血或碎面甲次数；
- 剩余未使用量。

使用整数累计器保存“累计 3 治疗 = 1 碎面甲次数”或“累计 2 治疗 = 1 蓝血”，避免每次小治疗丢精度。

## 5. 组合键与输入抢占

文件：`Core/Input/InputChordRouter.cs`

难点：`下 + 治疗` 既可能切专属状态，也可能是原版治疗；`上 + 治疗` 可能进入超级亡怒；蓄力 + 治疗触发专属技能。

规则：

- 先采样一帧输入快照，再由优先级表匹配。
- 匹配成功返回 `ConsumeHeal/ConsumeAttack`，游戏适配层决定是否阻止原输入。
- 同一帧最多执行一个排他动作。
- 菜单、过场、坐椅子、无控制权时不解析。
- 允许每个纹章注册条件，不在路由器中写纹章分支。

## 6. 虚拟工具库存与资源事务

文件：`Core/Resources/ResourceLedger.cs`、`VirtualToolService.cs`

“无库存消耗，而是消耗碎片/丝线”不能先生成工具再修改库存，否则中断或异常可能复制物品。使用事务：

1. 预检查资源、状态和冷却。
2. 预留资源。
3. 调用原版工具动作。
4. 动作成功后提交；失败或异常回滚。
5. 原版库存保持不变。

建筑师念珠弹夹切换也使用同一事务框架，切换形态时先归还旧弹夹，再按新倍率装填。

## 7. 可重入无敌帧

文件：`Core/Combat/InvulnerabilityLeaseService.cs`

每个来源申请一个 lease：`HunterDash`、`WitchDash`、`RuneRageCast`、`CurseHealAttempt`。只有所有 lease 都释放后才恢复可受伤。每个 lease 有超时，场景切换/死亡时统一清理。

这比直接设置 `isInvincible = true/false` 安全，因为两个效果重叠时，一个结束不会错误关闭另一个效果。

## 8. 动态 Harmony 目标解析

文件：`GameInterop/Binding/DynamicPatchResolver.cs`、`config/game-bindings.json`

游戏更新后类型名或签名可能变化。解析流程：

1. 按程序集与完整类型名候选查找。
2. 按方法名候选、参数数目、参数类型、返回类型筛选。
3. 多匹配时拒绝自动选择并输出候选。
4. 可选验证 IL 指纹或调用字段。
5. 解析失败只禁用依赖该绑定的 Feature ID。

不要用“第一个叫 TakeDamage 的方法”。

## 9. 纹章模块示例

文件：

- `Features/Crests/HunterCrestModule.cs`
- `Features/Crests/SilkMotherCrestModule.cs`
- 其余模块为同样的注册骨架。

模块只做三件事：

1. 订阅统一事件。
2. 调用核心服务改变状态或产生效果命令。
3. 向 UI 发布投影。

模块不应直接查找 GameObject、不直接反射、不直接写 PlayerData。

## 11. Agent 实现时的硬性检查

- 每个事件订阅都有对应解除。
- 每个协程在换纹章/死亡/场景切换时可取消。
- 追加伤害带来源标签，默认不递归。
- 所有资源消耗通过账本事务。
- 所有无敌通过 lease。
- 所有临时上限/等级通过投影，不直接永久写存档。
- 所有反射只在启动或场景绑定阶段执行并缓存。
- 所有不确定游戏成员名都进入绑定配置和探针报告。
